# AgentENV C++11 — Skeleton

A C++11 architectural port of [kvcache-ai/AgentENV](https://github.com/kvcache-ai/AgentENV).

> This is a **skeleton project** produced as Option B of the port plan:
> - Complete CMake workspace mirroring the Rust workspace crates.
> - Header-first API design: every Rust `trait` / core `struct` is mapped to a C++11
>   abstract class / value type.
> - `.cpp` files stub the bodies with `throw std::runtime_error("not implemented")`
>   so the whole thing compiles and links.
> - `docs/RUST_TO_CPP_MAPPING.md` explains the language-idiom translation table.
>
> **This skeleton is not runtime-functional as a whole.** It is a scaffold
> being grown into a working implementation, module by module. One object now
> covers start / pause / resume / stop (`FirecrackerSandboxBackend`), exercised
> end to end against a stand-in VMM. Snapshot, restore, fork and
> resume-from-snapshot are still stubs.
> It has never been run against a real Firecracker on a host with KVM.
>
> Statements that used to live here were stale and are corrected rather than
> deleted, because each was load-bearing when deciding what to trust:
>
> - **"the overlaybd layer writer is not ported, so a memory capture would
>   produce an empty layer"** — it is ported. `storage/overlaybd/lsmt_rw.cc`
>   carries the read-write LSMT file and its commit path, and
>   `PublishMemoryOverlaybdLayer` builds on `lsmt::CompactTo` with a
>   `ProcessVmReader`-backed source, writing `<path>.tmp` and renaming on
>   success. The status rows below that still describe it as missing are wrong
>   on that point; what those rows get right is the *surrounding* work —
>   rootfs capture, `build_mem_snapshot_image_config` and
>   `resume_from_snapshot_config`.
>
> - **"the volume operations are still stubs"** — the volume *module* is now a
>   complete port: `VolumeManager` (create / empty + child backing / COW clone
>   / materialize / publish / reserve / remove / fork), the durable record and
>   catalog (`volumes/records/<id>.json`, `volumes/aliases/<name>`), and the
>   posix-fs document store with `flock` + atomic-rename + CAS. What *is* still
>   missing is the capture side: `SnapshotVolumes`, `FreezeAndSnapshotVolumes`,
>   `ThawVolumes` and `Fork` on `FirecrackerSandboxBackend` report
>   "not available in this build", so nothing drives
>   `VolumeManager::SnapshotVolumeState` in production yet.
> - **"`main.cc` still wires an in-memory metadata store, so a restart loses
>   every sandbox record"** — the in-memory store is only the hot index. It is
>   paired with `FileBackedSandboxPersister` (`main.cc`), whose `LoadAll`
>   restores the previous run *before* the orchestrator exists, so a paused
>   sandbox does survive a restart. Volume metadata never went through that
>   store at all: it lives in the repository under
>   `{backend.posix_fs.snapshot_store}/repository`.

## Build

Requires: **CMake ≥ 3.16**, a **C++11**-capable compiler (`gcc-4.8+` / `clang-3.4+`).

By default no external dependency is required — every `TODO` interface lives behind
`throw std::runtime_error(...)`.

```bash
mkdir build && cd build
cmake -DAGENTENV_BUILD_TESTS=ON ..
cmake --build . -j
ctest
```

Optional features (turned OFF by default; each enables a real backend):

| CMake option                | Enables                                                     |
|-----------------------------|-------------------------------------------------------------|
| `AGENTENV_WITH_LIBURING`    | ublk / overlaybd real IO (needs liburing ≥ 2.5)             |
| `AGENTENV_WITH_GRPC`        | scheduler / gateway gRPC service                            |
| `AGENTENV_WITH_HTTPLIB`     | HTTP API server (cpp-httplib bundled as single header)      |
| `AGENTENV_WITH_ROCKSDB`     | orchestrator persistent store                               |
| `AGENTENV_WITH_ZSTD`        | overlaybd compression                                       |

The ordering rules are the substance, and each is pinned by a mutation check: **the record is written before the alias is claimed**, so losing the claim must roll the record back — a committed record holding an alias it does not own is findable by id, invisible by name, and reconciled by nothing — but **the rollback is conditional on the document still holding what this commit wrote**, or a concurrent writer's record would be discarded; **`ensure_not_committed` reads untyped JSON**, because it must also block on a record this build's typed decoder would reject (a newer server's), and treating an unreadable record as "not committed" would overwrite a live snapshot's files and then, when the commit failed, delete them; **an explicit `committed: null` is *not* committed**, matching `is_some_and(|c| !c.is_null())`, or such a snapshot could never be published again; **the alias and committed checks run twice** — here to keep a doomed publish from uploading a memory image, and again inside `commit` for the atomic guarantee, and dropping either is wrong in a different way; **the manifest is stored after the artifacts it names**; **a failed commit deletes the stored files but never the shared content-addressed layers**, since another snapshot may already reference the identical bytes; **`attach_startup_manifest` reports `false` rather than an error when the snapshot is gone**, because the pack is built after publication returns so a delete can legitimately win, and the caller uses that `false` to remove a blob nothing would otherwise collect — while an *uncommitted* record is a caller bug and must error, or the manifest is silently dropped. `commit` computes the committed record rather than reading it back: `UpdateDocument` returns the document it was applied to, i.e. the state *before* the write. Userinfo is **dropped, not refused** — upstream reaches the authority through `Url::host_str()`, which never includes it, and rebuilds `repo_blob_url` from the parsed registry, so a credential cannot reach the string that is cached and logged *and* a recorded URL carrying one still resolves; refusing it instead would fail the rollback inside a snapshot delete, leaving a "deleted" snapshot published. Tokens are issued with scope `push,pull` even for a delete, since ACR issues one token per repository and a pull-only scope cannot remove a manifest. **`TOKEN_EXPIRY_SKEW` is subtracted from every TTL** so a token is replaced slightly before the registry stops honouring it — without it, a token expiring in flight produces a 401 that reads as a credential failure — and a TTL shorter than the skew saturates to zero, i.e. is never cached, rather than going negative and caching forever. `Retry-After` wins over the exponential backoff; its HTTP-date form is ignored rather than mis-parsed. The token realm is validated for https too, because it is server-supplied and a downgraded realm would send the registry password over plaintext. Docker credentials come from `auths` (the base64 `auth` field first, since that is what `docker login` writes, splitting on the *first* colon so a password containing one survives), then `credHelpers`, then `credsStore` — a helper being asked about the address it was keyed by, not the registry name, and a non-zero helper exit meaning "no credentials" rather than failure; a config that exists but will not parse *is* an error, since skipping it would fall back to anonymous access and report the eventual 401 as a permission problem, hiding the typo. **`rollback_publication` succeeds with a warning on an unparsable `repoBlobUrl`**: it runs inside a snapshot delete, and such a publication can never be rolled back by any number of retries, so failing would wedge the delete forever on a record that is already unreachable. `delete_snapshot` unwinds publications in **reverse** order and warns past each failure, which is the same trade — a registry that is down must not pin the record, yet the attempt has to come first, because once the record is gone nothing names the publications. Driven over an injected transport that records every request, so the *sequence* (401 → token → retry) is asserted rather than only the final answer. `source_image.rs` is ported in full: it plans, lower by lower, whether a push reuses a blob the registry already holds or uploads a delta produced on this host. Every unmodelled shape is **refused rather than approximated**, because a mis-classified lower does not fail at plan time — it yields a manifest naming a blob nobody uploaded, and the image only breaks later on another machine. Remote lowers must all precede local deltas, since the lowers are the layer stack bottom-up and a remote lower below a local delta would silently reorder it; a sparse overlaybd delta is planned with **no** descriptor, because the uploaded bytes are the dense rewrite and hashing the file would record a digest for content the registry never receives; a recorded digest/size is trusted over re-measuring, so the manifest and the config cannot name different blobs; and only a sandbox's own runtime-generated rootfs delta may be uploaded, so a cached remote blob that merely happens to sit on this host is never published. `manifest.rs` is ported in full (see `snapshot/acr_manifest`). From `publisher.rs`, the **tag layer** is ported: the tag is validated *before* any blob is uploaded, because a tag rejected late would leave the blobs pushed with no manifest naming them, so the next publish re-uploads them and nothing collects the orphans. A per-drive tag hashes the **original** drive id rather than the sanitised text — sanitising alone collapses `data:1` and `data/1` onto `data-1` and the 32-character cap collapses every id sharing a long prefix, so without the hash two drives of one snapshot would publish to the same tag and the second would overwrite the first. One character maps to one `-`, so a multi-byte character does not become three. **Not ported**: `publisher.rs`'s `export` itself, which is blocked on three further modules rather than on itself — `AcrClient`'s push methods (`ensure_manifest_absent`, `blob_exists`, `upload_blob_bytes`, `upload_blob_with_descriptor`, `put_manifest`), and `write_dense_overlaybd_layer_to_file`; also the `regctl`/`service` exporter selection. `prepare_layer_upload` is now ported (see `snapshot/recontainerize`), though its raw→zfile branch still refuses, so an `export` built on it would be correct only under `publish_compression = false` |

| `snapshot/repository/oss` documents + client | `src/repository/backends/oss/{documents,client}.rs` | The shared-catalog half of the OSS backend: the document layer's **ETag compare-and-swap** (read with a version token, update `If-Match`, create `If-None-Match: *`, jittered 20→500 ms backoff, 32 attempts) over an injected `ObjectStore`, plus `OssClient`, the SigV4-signed S3/MinIO implementation of that interface on the existing `http::Transport`. Those are reclaim *policy*, so the guest would have dropped pagecache on a completely different schedule, and the old test only substring-matched `damon_reclaim.enabled=Y` so nothing caught it; it is now asserted byte-for-byte against `config/default.toml`. The validators are deliberately **three** methods, not one: `ValidatePersistedArtifacts` inspects only recorded artifacts, `ValidatePersisted` adds the snapshot's own files, and `Validate` adds this host's launch dependencies (Linux, the firecracker binary) — a paused state is decoded and checked on nodes that are *not* about to resume it, so requiring a local binary there would reject a valid snapshot. Two asymmetries are load-bearing: `rootfs_virtual_size` absent is legal at boot ("read it from the image") but illegal on resume, since a restored guest expects the exact device it was captured with; and an empty `tools_drive_version` is refused rather than defaulted, because resuming against a different tools release would swap the guest's userland underneath a restored memory image. Also collapses the C++-only `ExtraDriveSpec` into the real `ExtraDrive` — a parallel type carrying "the fields relevant to validation" is exactly how the two copies drift |
| `sandbox/firecracker` boot args + disk limits | `src/sandbox/firecracker/sandbox.rs` | The decisions inside the backend that do not need a live VMM. **DAMON**: `DamonMonitorRegion` reproduces Firecracker's per-architecture guest memory layout — x86_64 is identity-mapped up to 3 GiB, then skips a 1 GiB hole, then 257 GiB past 255 GiB; aarch64 starts DRAM at 2 GiB, so the window is *shifted*, not merely resized. A wrong bound here does not fail loudly, it just points the kernel's reclaim monitor at memory the guest does not own. `AddDamonMonitorRegion` treats an operator-supplied region as intent and leaves it untouched even when only one bound is given, with `start=0 end=0` as the explicit opt-in to substitute the computed values. **Disk rate limiting** carries the subtler contract: `PUT /drives` at fresh boot may omit the limiter entirely, but `PATCH /drives` on resume reads an *absent* bucket as "leave unchanged", so a snapshot-inherited limit cannot be cleared by omission. `ReconcileDiskRateLimiter` therefore always sends **both** buckets, starting from the `size == 0 && refill_time == 0` disable sentinel and replacing only what this node configures — and the sentinel needs both fields zero, since a mixed bucket is rejected as invalid and would fail the resume. Refill is pinned to 1000 ms so configured `*_per_sec` values *are* the sustained rate, and a burst of 0 is omitted rather than sent, because Firecracker only grants a burst when the field is present. Also `BuildDrivesBootArg` (`vda` = tools, `vdb` = user image, so extra drives begin at `vdc`) and the rootfs-first ordering of image config paths |
| `api/impls/sandbox` (validation half) | `src/api/impls/sandbox.rs` | Request validation and projection. The load-bearing rule is the domain allowlist: domain inspection only covers HTTP/HTTPS, so a policy naming domains *without* an explicit ALL_TRAFFIC deny would leave every other port open while reading as a restriction — it is refused. IPv6 CIDRs are rejected rather than ignored (the runtime installs only v4 rules, so an accepted v6 rule would be an unenforced restriction), `diskSizeMB` must be a whole number of GiB because the block layer allocates in 1024 MiB units, and `allowInternetAccess` is a genuine tri-state that maps `Default` back to JSON null so a client can tell "not set" from "denied". Handlers stay with the generated route enums |
| `api/impls/image_build` (decisions) | `src/api/impls/image_build.rs` | Dockerfile HEALTHCHECK translation and the build-session state machine. A mis-rendered healthcheck becomes the template's readiness gate, so an unrecognised form is an error rather than a silent skip — "always ready" would hand out a sandbox before it works. Exec-form arguments are quoted individually because the pieces are re-joined into one shell string. Every session transition is one-way and guarded: a cancelled build can never be observed as ready (which is what stops a client tunnelling into a sandbox being torn down), publishing requires having been ready, and terminal states never re-transition. The tunnel/worker half needs the transport stack |
| `image/cache` operation holds | `src/image/cache/service.rs` | The lease that stops GC collecting commits an in-flight resolve/import/GC depends on. Owners are uniquely numbered even for the same operation name: sharing one would let the first operation to finish release the second's protection while it still runs. The lazy form writes nothing until the first commit is actually protected, because most resolves hit a cached config and protect nothing. Release is best-effort and never escalates — leaving a hold behind costs disk, dropping one early costs a running operation its inputs. Rust's `Drop` becomes RAII |
| `api/impls/template_helpers` | `src/api/impls/template_helpers.rs` | Translates an E2B-shaped build request into a `TemplateBuildSpec`. The load-bearing detail is step numbering: one client step can expand into several internal steps (`ENV A=1 B=2` → two `Env` steps), and `StampSourceSteps` back-fills the client index over that range so both halves report as client step 1 rather than shifting every later step's reported position. Also: unsupported inputs are rejected rather than ignored (a non-blank `filesHash` means the client staged files for a COPY; `name:tag` would silently build the untagged template), and error messages quote the caller's original step spelling, not the upper-cased match key. The request DTOs are generated types upstream and are declared as plain data here |
| `api/impls/volumes` | `src/api/impls/volumes.rs` | `ResolveVolumeMounts` with its reservation rollback — a failure anywhere in the loop releases every lease the call made, so a half-resolved request cannot leave volumes leased to a sandbox that never launched. Mount-path overlap is checked **component-wise** (Rust's `Path::starts_with`), so `/mnt/a` and `/mnt/ab` may coexist while `/mnt/a` and `/mnt/a/b` are rejected. Plus the `VolumeError` → status map (the 409 group being "exists but unusable right now"), the record projection (internal fields withheld), and mode parsing that rejects rather than defaults. Handler methods themselves are bound to the generated route enums and are not ported |
| `api/impls/admin` | `src/api/impls/admin.rs` | `NodeSnapshot` → `Node` / `NodeDetail` projection, keeping the one shape difference (`sandboxStartingCount` is collection-only) and reporting paused reservations separately from live allocation. Disabled observability yields an empty list rather than a synthetic node, because a partial node is indistinguishable from a real one to a scheduler |
| `api/impls/attached_drives` | `src/api/impls/attached_drives.rs` | validation order preserved (drive id → mount path → sub path → size → image), uniqueness enforced on the *resolved* mount path so two drives that both omit it collide here rather than at launch, `diskSizeMB` required to be ≥1024 and GiB-aligned, and image resolution deferred to a second pass so a malformed request fails before any registry work |
| `snapshot/p2p` | `src/snapshot/p2p.rs` | `SnapshotP2pArtifact`: fixed per-snapshot keys (`snapshot/v1/artifacts/<id>/<name>`) plus digest- and uuid-keyed overlaybd layer artifacts. `local_overlaybd_layers` reproduces both publication guards — a raw layer whose digest is absent from the committed record is *not* published (publish-time compression recontainerized it as zfile, so the raw-digest key would never be looked up), and uuid-keyed publication is gated on the committed uuid set. Every failure path is a skip-with-warning, since P2P is an optional acceleration path |
| `storage/overlaybd` layer metadata | `storage/overlaybd/src/layer/layer_metadata.rs` | `ReadOverlaybdLayerUuid` / `ReadOverlaybdLayerVirtualSize` over the sealed trailer, with Rust's "unparseable uuid ⇒ nil" behaviour preserved (nil is the empty string here) |
| `image/cache` metadata graph | `src/image/cache/graph.rs` | `ImageCacheMetadataStore`: schema-version reconcile (wipes on mismatch), hard-commit object records with merge-preserving P2P key sets, config→hard and the mirrored hold→hard / hard→hold edges, `rebuild_from_configs` that fails closed on a malformed config, LRU touch on every resolve, and the store-backed capacity-eviction planner |
| `sandbox/runtime_versions` | `src/sandbox/runtime_versions.rs` | The `--version` probes recorded with a snapshot. The *parsers* were already here (`snapshot/version.cc`) and tested — but nothing in production called them, so a capture recorded no runtime versions at all, and those versions are what a restore checks before resuming a VM against a kernel or VMM it was not captured on. **Only the envd probe is fatal**: the kernel and VMM readings are diagnostics and degrade to `"unknown"` with a warning, while the envd version gates whether a restored sandbox can reach its guest agent, so `"unknown"` there would let a resume proceed against an envd the snapshot was never captured against. The VMM is asked **on the host** and the other two **inside the sandbox** — collapsing the two injection points would run `firecracker --version` in the guest, where it does not exist — and the host probe keeps upstream's 5 s timeout, because an optional probe that hangs must not hang the capture. stdout and stderr are combined whichever way round they arrive, since firecracker has printed its version to either. Run sequentially rather than through `tokio::join!`: there is no async runtime here, and three short probes do not justify threads whose only effect is to reorder log lines |

| `snapshot/image_export/{regctl,service}` | `src/snapshot/image_export/{regctl,service}.rs` | Rootfs image export: resolve the target, compare the deterministic manifest digest, upload only what the target lacks. **The three transfer shapes are a cost decision, not a correctness one** — a cross-repo `blob copy` within one registry moves no bytes, while `blob get \| blob put` across registries moves every one of them twice — so the tests assert the *argv* chosen per layer, since all three leave the blob in the right place. `BlobPipe` joins the two children with an OS pipe so a multi-gigabyte layer never enters this process; Rust pumps it with `tokio::io::copy`, which is the same memory guarantee by a different route, and the consequence of having no pump is that a truncated transfer surfaces as `put` failing its digest check rather than as a separate pump error. **An existing manifest at the ref is refused, never overwritten**: repointing the tag would orphan the manifest already there, making the layers it names collectable, and anyone pulling it would silently get different bytes — a tag is cheap to choose, an overwritten one is not recoverable. An identical digest is `reused` with nothing transferred. The manifest goes **last**, after every blob it names, because a manifest naming absent blobs is an image a puller cannot distinguish from a corrupt one. The `blob head` probe precedes every transfer, which for managed layers is the difference between reading a path and downloading gigabytes. An OSS-managed layer is recorded as an *external* ref carrying a synthetic `s3://` URL, and that marker has to win over the external branch or `regctl` would be aimed at a host serving no registry API; same-registry-and-repository with the blob absent is `ArtifactNotFound`, since there is nowhere to copy from. Managed layers are size-checked before upload — the registry would reject the digest anyway, but only after the bytes were sent and far from the cause. Rust's `ManagedLayerLocator` enum becomes an injected functor: its two arms are genuinely different operations (validate in place vs download) and this keeps the OSS client out of the header. `ExportRootfsImage` owns a scratch directory through an RAII guard so it is removed on every early return, and separates an unknown lookup (404) from a record whose build has not finished (invalid request) — collapsing them would answer "does not exist" for a template that is still building. **Not ported**: the `regctl`-vs-ACR exporter selection policy |

### Removed rather than left in place

- **`snapshot::Manager` / `snapshot::Repository` / `snapshot::MockRepository`** (6 files) were skeleton-era inventions that only referenced each other — zero callers tree-wide — yet still compiled. They were actively misleading: `snapshot/repository.h` declared a `class Repository` that shadows the real `SnapshotRepository` when reading, and `snapshot/manager.cc` hard-coded `/tmp/agentenv_snap_` with `created_at_ms = 0; // TODO: use system clock`. Anyone opening `src/snapshot/manager.cc` would conclude snapshot management was ported. `SnapshotMeta`, which existed only to serve them, went too.
- **`MakePosixFsRepository(root_dir)`** took a repository root, ignored it, and returned an `InMemorySnapshotRepository`. A caller trusting the name got a repository whose every document call answered `unsupported operation: repository documents`, with its data nowhere near the root it passed in. Nothing called it — `main.cc` already builds `posixfs::PosixFsSnapshotRepository` directly, which is the only way to supply both the catalog and artifact stores the backend needs — so a factory that cannot take those is not a factory for this backend. Removed rather than repaired; `docs/ARCHITECTURE.md` had been describing the stub as a known limitation instead.
- **`AGENTENV_LOG` no longer takes varargs.** `AGENTENV_WARN("a=", a)` expanded to `_oss << "a=", a` — the comma operator, which evaluates `a` and discards it. That compiled silently and truncated the message at the first comma, so the one value worth logging was the one that vanished. Six such calls existed; the two in `repository/oss/lease.cc` were worse, passing `printf` format strings to a streaming macro, so the log would have read `key=%s holder=%s` with both values lost. `-Wunused-value` catches only the subset whose dropped argument has no side effect — it missed exactly those two — so the macro now takes one named parameter and every occurrence becomes a compile error instead.

### Known gaps

The per-module 🟩/🟨 table that used to be here has been **deleted rather than
updated**. Every row of it claimed "header done, cpp stubbed", which stopped
being true module by module until the table said nothing checkable — and two
rows (`snapshot / manager`, `snapshot / repository`) pointed at files that no
longer exist. A status table that has to be trusted on faith is worse than no
table: it is what you consult *instead of* reading the code.

What follows is the list of things upstream does that this tree does not, kept
as a list of Rust paths so it can be checked against the source. The same
applies to `docs/RUST_TO_CPP_MAPPING.md`, whose §11 file map is stale (it
names `src/image/image.cc`, `src/api/dto/` and a single-file
`src/snapshot/repository.cc`, none of which exist); read it for the idiom
table, not for the layout.

**Absent entirely** — no corresponding symbol anywhere in this tree:

| Rust | Why it matters |
|---|---|
| `src/sandbox/tools_image.rs` + `deps::prepare_tools_image` + `FirecrackerSandbox::prepare_tools_drive` | One chain, and the reason `GetOrCreateSharedTools` is dead code. Upstream picks between two tools-drive shapes at launch: resolve the release's OCI reference to a local overlaybd `image.json` and attach it as a **shared ublk device**, or fall back to the legacy single-ext4 file. This tree always takes the second branch, because the chooser is missing. Not written rather than blocked |

**Ported but not yet called** — a third category, and the one most likely to
mislead: these have real implementations and tests, but no production caller,
so the behaviour they implement does not happen at runtime. Grepping for the
symbol finds it; grepping for its *callers* is what reveals the gap.

| C++ symbol | Rust caller that has no counterpart | Consequence today |
|---|---|---|
| `setup::CheckEnvironment`, `setup::RaiseFileDescriptorLimit` | `setup::ensure_environment` steps 1-3, 5, 6 | `src/main.cc` runs only this function's *networking* steps (runtime dir, netns reclaim, IPv4-forwarding precondition, capacity report). | `setup::deps::WriteGeneratedOverlaybdGlobalConfigs` | `deps::write_generated_overlaybd_global_configs` | The overlaybd global configs the ublk daemon reads are never generated, so cache directories, credentials and the p2p facade address are whatever already exists on disk |

| `overlaybd::CompactLayers` in zfile mode (and the `zfile::ZFileCompactWriter` it drives) | `SnapshotRepository::publish_policy` (`repository/interfaces.rs:95`, overridden by the OSS backend at `backends/oss/repository.rs:85`) | The whole compression path is now built and tested end to end -- `recontainerize.cc` compacts a raw layer into a real zfile and describes the compressed bytes.
