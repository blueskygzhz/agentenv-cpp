# AgentENV C++11 — Skeleton

A C++11 architectural port of [kvcache-ai/AgentENV](https://github.com/kvcache-ai/AgentENV).

> This is a **skeleton project** produced as Option B of the port plan:
> - Complete CMake workspace mirroring the Rust workspace crates.
> - Header-first API design: every Rust `trait` / core `struct` is mapped to a C++11
>   abstract class / value type.
> - `.cpp` files stub the bodies with `throw std::runtime_error("not implemented")`
>   so the whole thing compiles and links.
> - `docs/RUST_TO_CPP_MAPPING.md` explains the language-idiom translation table.
>
> **This skeleton is not runtime-functional as a whole.** It is a scaffold
> being grown into a working implementation, module by module. One object now
> covers start / pause / resume / stop (`FirecrackerSandboxBackend`), exercised
> end to end against a stand-in VMM. Snapshot, restore, fork and
> resume-from-snapshot are still stubs.
> It has never been run against a real Firecracker on a host with KVM.
>
> Statements that used to live here were stale and are corrected rather than
> deleted, because each was load-bearing when deciding what to trust:
>
> - **"volume capture is refused, so a volume can only lose writes loudly"**
>   — it was refused at three of its four doors. `snapshot_volumes`,
>   `freeze_and_snapshot_volumes` and `snapshot` (via `PauseToDir`'s flush
>   check) all refuse a sandbox holding a writable persistent volume, because
>   sealing needs the overlaybd layer writer and the flush needs an envd
>   client. **`pause` and `fork` did not**, and both now do.
>
>   Worth spelling out why that was a silent data loss rather than a partial
>   capture, because nothing downstream of it is wrong: upstream's
>   `pause(None)` is not a bare VMM pause — it routes through `pause_to_dir`,
>   which flushes the volumes and seals each upper into a new commit layer.
>   With the pause allowed through unsealed, the record moves to `Paused`; a
>   later delete sees `previous_state != Running` and skips
>   `freeze_and_snapshot_volumes`, *exactly as upstream does*;
>   `publish_sandbox_volume_backings` then publishes the volume's `image.json`
>   **lowers**, which is also exactly upstream (`store_disk_layers` iterates
>   `lowers` and nothing else) and is correct there only because the seal has
>   already folded the run's upper into them; `Stop` finally removes the work
>   dir and `extra-drive-runtime-<id>/upper.data` with it. Every link after
>   the pause is aligned, so the pause is the one that had to refuse.
>
>   `fork` is one step removed: the parent keeps running so its upper survives,
>   but upstream forks through the same full `pause`, so each child was being
>   built from a capture naming the *pre-seal* lowers and would boot cleanly
>   while silently missing every write the parent had made. Refused too.
>
>   Pinned by `tests/mutate_volume_capture_guards.py` (10/10), which re-opens
>   each door in turn — including refusing only *after* the guest is frozen,
>   and reporting the refusal as `Terminal` so a still-healthy sandbox gets
>   condemned. **Still missing, unchanged:** the layer writer and the
>   guest-dispatching executor that would let any of the four succeed, so a
>   sandbox with an exclusive volume can currently be neither paused, forked,
>   snapshotted nor deleted.
>
> - **"a resume cannot get a memory block device, because this port has no
>   ublk daemon client"** — it has one, and had one when that was written.
>   `ublk::DeviceManager::GetOrCreateSharedMem` is ported in full, refcount
>   and weak table included, and `FirecrackerSandboxFactoryImpl` already hands
>   that same manager to the fresh drive plan and to `ResumeDrivesFor`. What
>   was actually missing was the call: both resume paths set
>   `mem_device_path` from a *test-only* hook, so every production resume died
>   in `BuildResumeSequence` on an empty path, blaming a client that was wired
>   up two lines away. `StartResumeInstance` now acquires the device where
>   Rust's `acquire_shared_mem_device` does, holds the handle in
>   `FreshDriveResources::AdoptSharedMem` for the life of the sandbox (Rust
>   `resources.mem_ublk_device`) and drops it in `Release` after the VMM has
>   stopped. Two deliberate divergences: the device is acquired *before* the
>   work dir and network slot rather than after, because the path has to be
>   baked into the `SnapshotLoad` step — this releases strictly less on an
>   early return, and costs a refcount rather than a creation; and the memory
>   image is opened under `memory_snapshot.overlaybd_global_config_path`, a
>   separate `ResumeDrivePlan` field from the drives'
>   `ublk.overlaybd.global_config_path`, which is what upstream reads too.
>   **Still unverified against a real daemon** — no test drives the acquiring
>   branch end to end, only the refusal when no manager is configured.
>
> - **"the overlaybd layer writer is not ported, so a memory capture would
>   produce an empty layer"** — it is ported. `storage/overlaybd/lsmt_rw.cc`
>   carries the read-write LSMT file and its commit path, and
>   `PublishMemoryOverlaybdLayer` builds on `lsmt::CompactTo` with a
>   `ProcessVmReader`-backed source, writing `<path>.tmp` and renaming on
>   success. The status rows below that still describe it as missing are wrong
>   on that point; what those rows get right is the *surrounding* work —
>   `resume_from_snapshot_config`.
>
> - **"rootfs capture and `build_mem_snapshot_image_config` are missing"** —
>   both are ported. `build_mem_snapshot_image_config` lives in
>   `firecracker/mem_image_config.h`, and the rootfs capture half is
>   `firecracker/overlaybd_restack.h`: `RestackTargetUpperDataPath`,
>   `StageOverlaybdSnapshotFromLiveRuntime`, `RestackSnapshotOverlaybdDevice`
>   and `RestackSnapshotOverlaybdRootfs`, with the ublk seal injected as a
>   `SnapshotRestacker`. `PauseToDir` now drives both — it writes
>   `mem_image.json`, restacks the rootfs and assembles a
>   `SandboxSnapshotManifest` — and `FirecrackerSandboxBackend::CaptureToDir`
>   exposes that, leaving the guest paused as upstream does.
>
>   What remains is the step *above* it, and it is now only one step:
>   `ApiImpl::CreateSnapshot` is wired (`POST /sandboxes/{id}/snapshots`
>   captures, snapshots the mounted volumes and publishes), but it goes through
>   `Snapshot()` — as upstream's API path does — not through `CaptureToDir`.
>   `CaptureToDir` is the *template* entry point, which leaves the guest
>   paused, and `TemplateBuilder`'s sandbox-driving half is still the one open
>   end calling it. `CaptureToDir` is also deliberately **not** on the
>   `SandboxBackend` interface — see the `template/runner.rs` row for why.
>
>   `Snapshot()` now returns a `CapturedSandboxSnapshot` (manifest +
>   directory) rather than a bare path, because the publisher has to know what
>   was captured; re-deriving the manifest by reading the directory back would
>   let the two disagree. It refuses a capture with no manifest rather than
>   handing back a default-constructed one — which would commit a record
>   naming an empty backend and files at `/` — and it does so *after* the
>   resume it owes, since `Recoverable` is a promise the sandbox is running.
>
> - **"the extra drives are captured along with the rootfs"** — they were not
>   captured at all. Rust `snapshot_extra_drives` had no counterpart, and the
>   consequence was not a missing feature but a *wrong manifest*: `PauseToDir`
>   described each drive straight off the launch config, so every entry named
>   the drive's **source image** config and its **requested** size. A restore
>   from such a snapshot opens each data disk's pre-boot stack — cleanly, with
>   none of the writes the sandbox made — and `attachedDrives` being wired into
>   both create routes is what made that reachable. Two smaller faults rode
>   along: volumes were left *in* the manifest, where they both inflate
>   `physical_extra_drive_count` and get recorded as drives to recreate rather
>   than slots to rebind; and `volume_drive_slots` stayed at the constructor's
>   zero, so a restore read the capture as having no rebindable slots at all.
>
>   The loop is now `SnapshotExtraDrives`, a **free function** rather than a
>   backend method, because every decision it makes is a function of its
>   arguments — which is also what lets it be tested without a ublk daemon.
>   `PauseToDir` seals the drives inside its rootfs branch (sealing is
>   irreversible, so a capture that cannot be described must not consume the
>   running sandbox's uppers), then builds the manifest from the *sealed*
>   drives with volumes filtered out. Three rules carry consequences and are
>   pinned by `tests/mutate_snapshot_extra_drives.py` (13/13): each drive is
>   sealed against **its own** device (upstream's `bail!("extra drive
>   bookkeeping mismatch")` guards the pairing); a **volume** seals into its
>   own backing directory under a name unique per pause, because it reuses one
>   directory across pauses and a fixed name would overwrite a lower its live
>   `image.json` still references — corrupting the stack instead of extending
>   it; and the recorded size is the device's **actual** virtual size, since a
>   restore sizes the ublk device from it before opening the stack.
>
>   Note that the earlier note above — "the overlaybd layer writer is not
>   ported" — was also the wrong diagnosis *here*: the production sealer
>   `DeviceManager::RestackSnapshotDevice` existed all along and the rootfs
>   path was already using it. What was missing was only this loop.
>   **Still unlocked:** the manifest's volume filter. Reaching that branch
>   needs at least one *sealed* drive, which needs a live ublk device, so no
>   test gets there today — `volume_drive_slots` and the bookkeeping mismatch
>   are covered, the filter is not.
>
> - **"sandbox timeouts are enforced"** — they were not enforced at all.
>   `evict_expired_sandboxes` is ported in full and had two tests;
>   `auto_evict_interval_ms` is parsed and defaults to 1000 with a test of its
>   own (`test_cfg`); every sandbox gets an `expires_at` and the store answers
>   `ListExpired`. What there was no counterpart to was
>   `start_auto_evict_task`: upstream's `new_inner_with_volumes` ends by
>   spawning the sweep, and `Orchestrator::New` built the orchestrator and
>   returned. So the sweep was dead code — no sandbox ever reached its
>   timeout, `timeout_action` (the field a caller sets to choose between pause
>   and delete) never ran once, and a leaked sandbox held its VM, network
>   slot, drives and image refs until the process died. Nothing reported it,
>   because the config kept saying eviction was on.
>
>   This is the fourth instance of the same defect class in this port
>   (`mem_device_path`, the `pause`/`fork` volume doors, `snapshot_extra_drives`
>   and now this): a component that is complete, tested and configured, with
>   zero production callers. It is worth naming as a class, because "is it
>   ported?" has repeatedly been the wrong question — the right one is "who
>   calls it?".
>
>   `New` now calls `StartAutoEvictTask(config.orchestrator.auto_evict_interval_ms)`
>   last, as upstream does, so the thread cannot sweep a half-built
>   orchestrator. Upstream holds a `Weak<Self>` so the task cannot keep the
>   orchestrator alive and selects on a `watch` channel so a shutdown is not
>   charged for the rest of a tick; here the thread is a member joined by
>   `StopAutoEvictTask`, called from both `Shutdown` and the destructor, and
>   the interval is a `condition_variable::wait_for` on a stop flag rather
>   than a sleep. The join is what makes `this` safe to capture: the sweep
>   reads the store, the handle map and the deletion locks, and a thread still
>   running after those members die is a use-after-free.
>
>   Pinned by `tests/mutate_auto_evict_task.py` (11/11), which unhooks the
>   driver, hard-codes the interval past the config, ends the loop after one
>   cycle or one error, and breaks the stop in all four of its available ways
>   (no notify, no flag, no predicate, no post-wait check — the last two being
>   the lost-wakeup and the one-more-sweep-after-shutdown cases). Writing it
>   was what showed that three of the tests only looked like they locked this:
>   "an expired sandbox stays put after shutdown" is true whether or not the
>   task was joined, because `EvictExpiredSandboxes` checks `IsShuttingDown`
>   itself; and a cycle *failure* cannot be provoked through a sandbox whose
>   pause fails, since the sweep logs and continues per sandbox and still
>   returns `Ok`. It needs a store whose `ListExpired` fails, which the only
>   production store cannot do.
>
>   **Still missing, same function:** `start_metrics_task`, upstream's other
>   constructor-spawned loop (`metrics_interval_secs` is parsed and unused).
>   **Not locked:** replacing the start guard with `detach()` — the abandoned
>   thread still exits on the flag, so what it leaves is a use-after-free
>   rather than a wrong value, and catching it needs a sanitizer build.
>
> - **"a snapshot record can be produced from an API route"** — from exactly
>   one, and the template build pipeline was fully ported and **unreachable**.
>   `TemplateBuilder` (`ExecuteAndPublish` / `BuildAndPublishWithId`) and
>   `TemplateBuildRecordFromV3Request` all existed with tests and no caller
>   outside them, because neither of the two routes that drive them upstream
>   was served. The record builder was the sharper case: it produced a
>   `TemplateWaiting` record that nothing stored, so the name it claimed was
>   never actually reserved and `TryStartBuild` had no record to find.
>
>   `POST /v3/templates` is now served, answering 202. It is the first of
>   upstream's two steps: validate, build the waiting record, and **commit
>   it** through `record_catalog::Create` (Rust `snapshot_manager.create`),
>   which is what claims the name. Committing is the whole point — without
>   the write, two concurrent requests for one template name would both be
>   told they had it, which is why `tests/test_api_template_build.cc` drives
>   the *real* OSS repository over an HTTP-level ETag stub rather than a
>   hand-written document store: the conflict is a compare-and-swap, and a
>   fake store would make the only interesting failure unobservable. Every
>   assertion reads the record back from the store, because the response is
>   exactly what a handler that built the record and dropped it would also
>   return.
>
>   `imageOnly` is **refused with a 501** rather than accepted and ignored.
>   Upstream sends it to `create_image_build`, which produces a reusable image
>   and no template record at all; ignoring the flag would answer 202 and hand
>   over the one artifact the request explicitly asked not to have, with the
>   tags pointing at it. What it needs is the Dockerfile build pipeline —
>   `ImageBuildRecord`, the buildkit worker and its log tunnel — none of which
>   is ported.
>
>   Pinned by `tests/mutate_api_template_build.py`, which unhooks the
>   commit in the two ways that still answer 202, turns each refusal into
>   silent success, and breaks every field of the request DTO. Two properties
>   are deliberately **not** pinned and the script says so: where
>   `RequireRepository` sits in the sequence (observable only for a request
>   that would also fail to build a record), and reading the response ids from
>   the stored record rather than the local one (`Create` never rewrites the
>   id, so the two are equal by construction — the guard is against a future
>   backend that does).
>
>   **Still missing:** the build itself. `POST
>   /v2/templates/{templateID}/builds/{buildID}` now validates and refuses
>   (below), so a template can be *reserved* over HTTP but not yet *built*,
>   and `aenv snapshot` / `aenv build` remain stubs.
>
> - **"`GET /templates` needs the template store"** — the 501 it answered said
>   so, and there is no template store, upstream or here. Templates *are*
>   snapshot records: `record_catalog::List` was ported and tested, the
>   `SnapshotListFilter::Templates()` filter existed, and this class already
>   held the repository that `CreateSnapshot` and `CreateTemplateBuild`
>   publish through. Only the call was missing — the stale diagnosis is what
>   made it look like a dependency problem rather than four lines.
>
>   Fixing it exposed a **second defect hidden behind the first**: the route
>   wrote a hard-coded `{"templates":[]}` body, where the 200 variant of
>   upstream's `TemplatesGetResponse` carries a bare `Vec<models::Template>`.
>   While the handler was a 501 that body never reached a client, so nothing
>   showed the shape was wrong as well as the content. This is the second time
>   in this audit that a refusal has been hiding a wrong answer behind it (the
>   first was `POST /sandboxes/{id}/snapshot`, singular, answering 204).
>
>   `TemplateModel::FromRecord` is Rust's `impl From<SnapshotRecord> for
>   models::Template`. Three of its rules carry consequences: a record's
>   `names` falls back to its id when it has no alias, because `names` is how
>   a client addresses the template and an empty list would make an
>   addressable one invisible; a sandbox-sourced record reports `Ready` rather
>   than its build's default `Waiting`, since it has no build and exists only
>   because a capture succeeded; and `buildStatus` is written in the
>   **lowercase wire spelling**, not `snapshot::TemplateBuildStatusToString`'s
>   capitalised record spelling — the two enums are both called
>   `TemplateBuildStatus`, and putting `"Waiting"` in a body whose schema
>   declares `"waiting"` is rejected by a generated client as an unknown
>   variant.
>
>   `tests/mutate_api_template_build.py` was extended to this route too.
>   Writing the new half caught two tests of mine that only looked like they
>   locked something: a corrupt catalog read as an empty list passed, because
>   I had no record that fails to decode (`List` refuses one rather than
>   skipping it, so the handler must not flatten that to 200); and
>   `lastSpawnedAt` being *omitted* passed a `kind() == Null` check, because a
>   const `operator[]` on an absent key yields a null `Json` — the assertion
>   had to move to the object's key set.
>
> - **"`POST /v2/templates/{templateID}/builds/{buildID}` is not available"** —
>   the diagnosis was right, the *scope* was not: the 501 was returned before
>   anything was checked, so every malformed start request was answered as an
>   unsupported feature. The route is upstream's second step, and what is
>   genuinely absent is only the last piece of it —
>   `TemplateBuildExecuteFn`, which boots a Firecracker sandbox and drives
>   start/capture/stop. Everything in front of that is ported.
>
>   So the handler now runs the **entire** upstream sequence and refuses at the
>   end: the two path segments must agree, `buildID` must parse, the record
>   must exist, `fromImage`/`fromTemplate` must not both be set, the step list
>   must translate into a `TemplateBuildSpec`. A caller with a bad body now
>   gets a 400 that names the field instead of a 501 telling them to wait for a
>   release that will not fix it.
>
>   The ordering is the point, and it is the opposite of what reads naturally.
>   The refusal must land **before** `TryStartBuild`, because that call moves
>   the record `waiting` → `building` and only a `waiting` record can be
>   claimed — claiming and then failing to build would leave the template
>   permanently unstartable, dead even once the executor lands. Refusing first
>   keeps the reservation intact, which makes the refusal idempotent: the same
>   request works unchanged later. Both properties are asserted against the
>   stored record, not the response.
>
>   One check is easy to read as redundant and is not: the record lookup
>   accepts an id *or* an alias, so `templateID` can resolve to a record whose
>   id is not `buildID` even after the two segments were compared as strings.
>   That is reachable because `SnapshotAlias::Parse` allows letters, digits,
>   hyphens and underscores — a template may be *named* after a uuid — and
>   building it would run against someone else's reservation and publish it
>   under their name. Upstream has it too (`pending_record.id != build_id`,
>   `template.rs`), with the same 400.
>
>   `fromImageRegistry` is **refused, not ignored**, and this is the one
>   refusal that is not about the missing executor: `RegistryAuth` is ported
>   but not wired into the build path, so honouring the body is impossible.
>   Ignoring it pulls anonymously, which either fails with the authentication
>   error the caller already solved or — worse — silently resolves a
>   *different, public* image of the same name and publishes it as their
>   template. Its own 400 (`fromImageRegistry` without `fromImage`) is checked
>   first, so a malformed credential block is reported as malformed.
>
>   `tests/mutate_api_template_build.py` covers all three routes (46/46). One
>   mutation was **removed rather than left as a passing survivor**: which
>   resources the handler sizes the spec from cannot be observed, because
>   `TemplateBuildSpecFromStartRequest` never fails on that argument and the
>   handler drops the spec after using it to validate the steps. The property
>   is asserted directly against the helper instead, and the script records
>   why — it becomes mutable at the call site when the executor lands.
>
>   **Still missing:** `TemplateBuildExecuteFn` and the background executor
>   around it (`capture_to_dir`, the build log stream, the task that polls the
>   record to `Ready`). That is the same block `aenv build` is stubbed on.
>
> - **`GET /templates/{templateID}/builds/{buildID}/status` and
>   `.../logs` were unrouted** — and between them they were the only answer to
>   "why did my build fail". `GET /templates` reports *that* a build failed:
>   it lists every template on the node, carries no failure reason and no log
>   line. `ReadBuildLogs` was ported with no caller at all, so the document
>   holding the answer could be written and never read back.
>
>   Both routes are now served, through upstream's shared `build_record` and
>   `query_build_logs`. The status body carries the record's error reason plus
>   the output of the step that failed — bound twice over, to that step and to
>   `warn`-and-above, because without the step filter it is the log of a build
>   that mostly worked and without the level filter the failing step's own
>   progress output buries its error.
>
>   The refusals are where the detail is, and two of them look wrong until you
>   see the client:
>
>   - A disagreeing `templateID`/`buildID` is a **404** here and a **400** on
>     the V2 start route. Upstream splits them and it is right to: the start
>     route is asked to create something from two ids and reports them as a
>     bad request, while these two are addressing `builds/{buildID}` under
>     `{templateID}`, and a build that is not under that template is not
>     there. Both 404s on this route are distinguishable by message, so a
>     client can tell "that pair does not go together" from "that build does
>     not exist". Pinned by reserving *two* templates and reading one under the
>     other's id — with one reservation the test passes either way, which is
>     how this first appeared as a surviving mutant.
>   - `limit` above 100 is **refused, not clamped**, and `limit=0` is a valid
>     request for nothing. Clamping would answer 200 with a short page, which
>     a caller cannot tell from a build whose log really is that short — so it
>     would stop paging early.
>
>   `source=temporary` is the one place the missing executor shows through, and
>   it is honest rather than stubbed: upstream reads a live in-memory buffer
>   first and falls through to the stored document. Nothing runs a build here,
>   so that buffer is always absent and `temporary` reads **empty**. Falling
>   through would hand a caller a *previous* attempt's output presented as the
>   running build's, which is exactly what they would act on.
>
>   A captured sandbox snapshot is refused as a template build. It has no
>   build block, so reporting it would describe it as permanently `Ready` —
>   the most launchable-looking answer the route can give, for something that
>   never ran. The guard behind it is load-bearing only because of a choice
>   *this* port made: Rust's `SnapshotSource` is an enum where `Sandbox` has no
>   `build` field, and the C++ version flattened it into one struct, so that
>   state is representable here and not upstream. No document can produce it
>   (`SnapshotSource::FromJson` reads `build` only under the `Template` key)
>   but any in-process caller can, which is what the test constructs.
>
>   Two of upstream's status overrides are **not** ported and are unreachable
>   rather than skipped: `build_sessions.is_starting` / `is_finishing` adjust
>   the reported status while an `aenv build` builder session is in flight.
>   `BuildSession` is ported, but nothing registers one — the builder routes
>   are unserved and `StartTemplateBuild` refuses before registering anything —
>   so both would be reading an always-empty registry. Upstream's
>   `image_build_record` fallback in `build_record` is absent for the same kind
>   of reason: `imageOnly` is refused at reservation, so no such record can
>   exist, and the 404 the fallback would return is the one already given.
>
>   `tests/mutate_api_template_build.py` is now 78/78 across the five routes.
>
>   **Still missing on these two routes:** nothing that is reachable. What
>   they report stays thin until the executor lands and starts writing build
>   logs — today the only writer of a build log document is a test.
>
> - **`volume/record` audited against `src/volume/mod.rs` field by field.** The
>   record half turned out to be faithful — struct fields and serde attributes,
>   `mounted_by`, `replace_owner`, `validate_catalog_update`, all fifteen
>   `VolumeError` messages, the `URL_SAFE_NO_PAD` cursor codec,
>   `is_valid_volume_component`, and the deliberate split between
>   `validate_name` (`InvalidName`) and `validate_volume_id` (`Storage`) — with
>   one real divergence:
>
>   `VolumeStatusParse` reported `unsupported volume status "x"` where upstream
>   has no hand-written parser at all and serde's derive produces `unknown
>   variant ..., expected one of ...`. That text is what the catalog surfaces
>   when a record fails to decode, and the file's own sibling `VolumeModeParse`
>   had already been aligned to serde's wording with a comment saying so, so
>   this was the one that drifted. Fixed. Note serde switches phrasing on the
>   variant count — two variants read "`a` or `b`", three or more read "one of
>   `a`, `b`, `c`" — which is why the two lines are *supposed* to differ, and
>   why asserting only one of them is how the drift survived.
>
>   Two gaps are recorded rather than closed, because neither is reachable or
>   fixable here:
>
>   - `sizeMb` is a `u64` upstream and `core::Json` has no unsigned kind, so
>     the representable range stops at `i64::MAX`. Unreachable through
>     upstream (`VolumeLimits::max_size_mb` caps a volume long before eight
>     zebibytes), and a hostile document in that range is refused rather than
>     truncated.
>   - Key *order* in the encoded document. `serde_json::to_vec_pretty` emits
>     declaration order; `core::JsonObject` is a `std::map`, so this emits
>     sorted. Compatible in both directions since neither parser is
>     order-sensitive, but it does mean a digest of a record document is not
>     portable between the implementations. That is a port-wide property of
>     `core::Json`, not of volumes.
>
>   New harness `tests/mutate_volume_record.py`, 62/62. Seven of its mutations
>   survived the first run and six were genuine blind spots — non-ASCII bytes
>   in `is_valid_volume_component`, a mode-only identity change, the
>   `TooManyMountedVolumes` payload in `operator==`, and a missing
>   `backingLayers`/`readOnlyMounts` defaulting to empty. The cursor-length one

A per-drive tag hashes the **original** drive id rather than the sanitised text — sanitising alone collapses `data:1` and `data/1` onto `data-1` and the 32-character cap collapses every id sharing a long prefix, so without the hash two drives of one snapshot would publish to the same tag and the second would overwrite the first. One character maps to one `-`, so a multi-byte character does not become three. The **push half** of `client.rs` is now ported too. `ensure_manifest_absent` runs *before* any blob is uploaded, so a tag that is already taken costs one `HEAD` rather than a full layer push, and **any** 2xx counts as taken rather than only a 200 — a published tag may already have been pulled, and replacing its manifest silently changes what that reference means. `blob_exists` is the deduplication that makes a re-publish of an unchanged layer free, and an error status is **not** collapsed to "absent": guessing absent would re-upload a layer the registry already holds while hiding the failure. `upload_blob_with_descriptor` validates the descriptor against the file *before* uploading — empty digest, zero size, or a size disagreeing with the file on disk — because the digest is what the manifest will claim and nothing downstream re-derives it, so a stale descriptor would publish a manifest naming a layer that is not what was sent. The chunked upload is `POST` to open a session, one `PATCH` per chunk, then `PUT ?digest=`: the `Content-Range` is bare **`<start>-<end>`**, with neither the `bytes ` prefix nor the `/<total>` suffix of the HTTP range header it resembles, and the completing `PUT` carries **no further bytes**, since everything already went out as chunks and repeating the tail would append it twice. A `Location` returned on a `PATCH` **relocates the session**, and a registry that moves it will not accept the old URL again. A retried `PATCH` reuses the same session and byte range, which OCI registries are expected to tolerate. `put_manifest` prefers the registry's `Docker-Content-Digest` over the locally computed one — that is the digest the registry will answer to later, and they differ only when it re-serialised the manifest — with the local digest computed up front so a missing header is answered rather than failed. ### Removed rather than left in place

- **`snapshot::Manager` / `snapshot::Repository` / `snapshot::MockRepository`** (6 files) were skeleton-era inventions that only referenced each other — zero callers tree-wide — yet still compiled. They were actively misleading: `snapshot/repository.h` declared a `class Repository` that shadows the real `SnapshotRepository` when reading, and `snapshot/manager.cc` hard-coded `/tmp/agentenv_snap_` with `created_at_ms = 0; // TODO: use system clock`. Anyone opening `src/snapshot/manager.cc` would conclude snapshot management was ported. `SnapshotMeta`, which existed only to serve them, went too.
- **`MakePosixFsRepository(root_dir)`** took a repository root, ignored it, and returned an `InMemorySnapshotRepository`. A caller trusting the name got a repository whose every document call answered `unsupported operation: repository documents`, with its data nowhere near the root it passed in. Nothing called it — `main.cc` already builds `posixfs::PosixFsSnapshotRepository` directly, which is the only way to supply both the catalog and artifact stores the backend needs — so a factory that cannot take those is not a factory for this backend. Removed rather than repaired; `docs/ARCHITECTURE.md` had been describing the stub as a known limitation instead.
- **`PosixFsRuntimeResolver`** (`snapshot/repository/posixfs/runtime.{h,cc}`) was not a stub -- it worked, and was the only resolver this tree had. It is gone because its shape was the defect: constructed from a repository **root path**, it could serve only backends whose bytes are reachable by path, which is why `oss` had no resolver and resume answered 501 there. Generalising it in place would have meant a class named for one backend holding an interface that abstracts over all of them. The header carried a note arguing the opposite -- that with no second caller, generalising would be speculative. That reasoning had it backwards: the second caller was missing *because* the resolver could not be built for it. See the `snapshot/resolver` row above.
- **`AGENTENV_LOG` no longer takes varargs.** `AGENTENV_WARN("a=", a)` expanded to `_oss << "a=", a` — the comma operator, which evaluates `a` and discards it. That compiled silently and truncated the message at the first comma, so the one value worth logging was the one that vanished. Six such calls existed; the two in `repository/oss/lease.cc` were worse, passing `printf` format strings to a streaming macro, so the log would have read `key=%s holder=%s` with both values lost. `-Wunused-value` catches only the subset whose dropped argument has no side effect — it missed exactly those two — so the macro now takes one named parameter and every occurrence becomes a compile error instead.
